# 保险行业 Agent：环节映射与落地路线图

> **配套文件**：[01-business-overview.md](01-business-overview.md)（业务全景）与 [02-full-diagrams.md](02-full-diagrams.md)（完整图集）。
> **本文件回答三个问题**：哪些环节值得 Agent 化、需要什么数据、按什么顺序做才安全可控。
> **口径**：融合中国大陆险资与香港实践；监管数值为示意，须按最新文件与公司内部制度校准。本文件为内部工作文档，含路线设计，不用于对外发布。

---

## 1. 三个结论

1. **保险资管 Agent 的差异化不在"更聪明的选股"，而在"把负债与合规变成硬约束"。** 通用投资 Agent 已有成熟骨架，保险侧缺的是 ALM 层与合规闸门层。
2. **先做数据与报告，再做研究与配置，交易执行永不自动化。** 保险行业是强监管、重留痕环境，Agent 的价值先体现在"省人时、少出错、可复现"。
3. **数字必须由确定性代码算，语言由模型组织。** 任何金额、比例、收益率、久期都应由脚本或系统计算，模型只负责解释、对比与写作；这是控制幻觉的唯一可靠方式。

## 2. 参考项目与借鉴边界

| 项目 | 借鉴什么 | 不能直接照搬的部分 |
| --- | --- | --- |
| TradingAgents | 分层编排、多空辩论、风控审批环节 | 面向二级市场短周期交易，无负债与偿付能力约束 |
| ai-hedge-fund | 角色化 Agent、可回测原型、组合经理机制 | 个人投资者视角，无监管比例与关联交易概念 |
| FinRobot | 分层平台设计（Agent 层 / 工具层 / 数据层） | 通用金融场景，需自行补保险科目与精算口径 |
| Qlib + RD-Agent | 研究自动化闭环、因子与模型治理、可复现流水线 | 以股票横截面为主，债与非标覆盖弱 |
| OpenBB | 统一数据接口层设计 | 公共数据源为主，无法替代内部数仓与精算系统 |
| ai-berkshire | 基于 Codex / Skill 的中文研究编排、方法论人格化 | 价值投资取向，不适用于保险负债驱动配置 |
| Vibe-Trading | MCP 工具化、回测审批闭环 | 交易执行导向，保险场景须去除自动下单 |
| FinGPT | 金融文本模型、舆情与情绪因子 | 模型需本地或私有部署以满足数据合规 |
| QuantsPlaybook | 中文量化方法论知识库的组织方式 | 研报复现内容需自行确认版权与使用范围 |
| ALM / 偿付能力类小众项目 | 随机 ALM 与 IFRS 17 / 偿二代现金流建模思路 | 代码成熟度低，仅作方法论参考 |

**生态判断**：截至 2026-09，GitHub 上的投资 Agent 生态集中在交易与研究侧（头部项目星标数万到十万级），而保险资管方向的 Agent 项目基本处于空白（保险侧多为核保、理赔、合同问答等单点小项目）。这意味着保险 Agent 的**框架定义权还在空位上**，但对数据与合规的要求也更高。

## 3. 环节 × Agent 化机会矩阵

自动化等级：**L0 全人工**（仅作参考）｜**L1 助手**（问答、摘要、检索）｜**L2 人审后采用**（生成初稿，人工签核）｜**L3 受控自动**（规则内自动运行，异常升级）｜**L4 自治**（仅限非决策类任务）。

| # | 环节 | 现状痛点 | Agent 形态 | 等级 | 主要输入 | 产出 | 优先级 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 1 | 数据接入与校验 | 多系统取数靠人工拼 Excel，口径易错 | 数据接入 Agent | L3 | 数仓、交易、估值、精算 | 标准化数据包 + 质量报告 | P0 |
| 2 | 制度与合同问答 | 制度分散在文件与邮件 | 知识库 RAG Agent | L1 | 制度、合同、内评报告 | 带出处的答案 | P0 |
| 3 | 月度报告与会议材料 | 手工拼接 2 到 3 天 | 报告生成 Agent | L2 | 持仓、收益、风险、归因 | 报告初稿 + 图表 + 口径说明 | P0 |
| 4 | 绩效归因 | 口径多、复算耗时 | 归因 Agent | L2 | 持仓、成交、基准、因子 | 归因分解 + 异常解释 | P1 |
| 5 | 宏观与利率研究 | 依赖个人经验，难沉淀 | 研究 Agent 群 | L2 | 宏观数据、曲线、政策文本 | 情景假设与观点卡片 | P1 |
| 6 | 信用与舆情跟踪 | 覆盖面不足，跟踪滞后 | 信用 Agent | L1 到 L2 | 财报、评级、新闻、公告 | 预警清单 + 评级跟踪表 | P1 |
| 7 | 负债与 ALM 测算 | 精算周期长，与投资端脱节 | ALM Agent | L2 | 现金流、久期、退保与赔付假设 | 久期缺口、匹配方案 | P1 |
| 8 | 情景与压力测试 | 频率低，情景单一 | 情景 Agent | L2 | 宏观情景、历史压力事件 | 压力测试结果与资本影响 | P1 |
| 9 | 限额与合规校验 | 人工逐条核对，易漏 | 合规 Agent | L2 | 监管规则、内部限额、持仓 | 通过 / 降规模 / 升级 / 否决 | P1 |
| 10 | 组合优化与配置建议 | 经验驱动，偏离理由不充分 | 组合优化 Agent | L2 | 负债约束、风险预算、观点 | 目标权重与偏离说明 | P2 |
| 11 | 估值与对账异常排查 | 人工排查耗时 | 运营 Agent | L2 | 估值、成交、托管对账 | 异常定位与处理建议 | P2 |
| 12 | 监管报送底稿 | 高度重复劳动 | 报送 Agent | L2 | 财务、偿付能力、持仓 | 底稿 + 交叉校验报告 | P2 |
| 13 | 评估与审计 | 缺少统一评估机制 | 评估与审计 Agent | L3 | 全链路日志与输出 | 准确率、覆盖率、留痕报告 | P1 |
| 14 | 交易执行与下单 | 时效要求高 | **不适用** | L0 | — | — | 禁止自动化 |
| 15 | 投资决议与签批 | 责任归属人 | **不适用** | L0 | — | — | 禁止自动化 |

**取舍原则**：优先做「高频、重复、可验证」的环节（第 1、3、9、13 项）；谨慎做「影响损益判断」的环节（第 10 项）；永不做「承担受托责任」的环节（第 14、15 项）。

## 4. 数据契约与字段清单

Agent 的能力上限由数据契约决定。建议先固化下表，再写代码。

| 数据域 | 关键字段 / 表 | 来源系统 | 更新频率 | 敏感级 | 支撑的 Agent |
| --- | --- | --- | --- | --- | --- |
| 持仓与交易 | 证券代码、账户、数量、成本、市值、久期、评级、行业、成交日期、对手方 | 投资交易系统 | 日 / T+1 | 高 | 数据接入、归因、风控、报告 |
| 市场数据 | 收益率曲线、指数行情、信用利差、汇率、波动率 | 行情商 / 中债 / 交易所 | 日 / 实时 | 中 | 研究、优化、情景 |
| 负债与精算 | 现金流、久期、退保率、赔付假设、准备金 | 精算系统 | 月 / 季 | 极高 | ALM、情景、报告 |
| 偿付能力 | 实际资本、最低资本、充足率、风险因子 | 偿付能力系统 | 季 | 极高 | 合规、优化、报告 |
| 财务与会计 | 科目、会计分类、公允价值、损益、减值 | 财务 / 总账 | 月 | 高 | 归因、报告、报送 |
| 限额与规则 | 监管比例、内部限额、授权矩阵、关联方名单 | 风控 / 合规 | 事件驱动 | 高 | 合规、风控 |
| 知识资产 | 制度、合同、研究报告、内部评级报告 | 文件库 | 事件驱动 | 中到高 | 知识问答、研究、写作 |
| 外部另类数据 | 舆情、新闻、产业链、招聘、卫星等 | 第三方 | 日 / 周 | 低到中 | 信用、研究 |

**三个必须先解决的数据问题**：

1. **时点一致性**：持仓、估值、市场数据的时点必须对齐，否则所有指标都不可比。
2. **口径字典**：同一个"投资收益率"在不同部门可能有三种算法，必须先定义唯一口径。
3. **穿透能力**：委外与基金持仓能否穿透到底层资产，直接决定风控与合规 Agent 的可行性。

## 5. 合规与治理红线

| 红线 | 具体要求 | 违反后果 |
| --- | --- | --- |
| 决策责任归属人 | Agent 只出建议，签批与责任在授权人 | 问责风险、监管处罚 |
| 禁止直连交易 | Agent 不接触下单接口，不生成可执行交易指令 | 操作风险、内控失效 |
| 数据不出域 | 内部数据不出内网 / 不出境，优先私有化部署 | 合规与数据安全风险 |
| 全链路留痕 | 输入、模型版本、工具调用、结论、签核人可追溯 | 无法审计与复盘 |
| 数值由代码算 | 金额、比例、久期、收益率一律脚本计算 | 幻觉导致决策错误 |
| 输出可验证 | 每个结论需附数据来源、计算过程与假设 | 无法复核 |
| 权限最小化 | 按角色划分数据与工具权限，敏感域单独授权 | 数据泄露 |
| 报送口径双人复核 | 监管报送与披露材料必须人工复核签批 | 报送错误、监管问责 |
| 模型上线审批 | 重要模型需验证、回测与变更管理 | 模型风险 |
| 对外脱敏 | 内部数据、持仓、客户与员工信息不进作品集与外部仓库 | 保密违约 |

## 6. 分阶段路线图

| 阶段 | 周期 | 目标 | 交付物 | 验收标准 |
| --- | --- | --- | --- | --- |
| Phase 0 数据与契约 | 2 到 4 周 | 把取数从人工变自动 | 字段字典、口径表、可查询数据集市 | 一键取出上月末组合久期、收益率、各类资产占比，口径与月报一致 |
| Phase 1 单点 Copilot | 4 到 6 周 | 低风险场景先见效 | 报告初稿生成、制度问答、数据查询 | 报告准备时间下降 70% 以上，事实性错误率低于 5% |
| Phase 2 研究 Agent 群 | 6 到 10 周 | 研究与归因可复现 | 宏观 / 信用 / 权益 / 另类并行研究 + 归因引擎 | 结论可溯源、可复现，同一输入两次运行结果一致 |
| Phase 3 决策支持闭环 | 8 到 12 周 | 打通负债到配置 | ALM 测算、情景压力测试、组合优化、风控与合规闸门 | 输出配置建议可上投委会，材料自动生成并含偏离说明 |
| Phase 4 受控执行与评估 | 持续 | 稳定性与治理 | 对账、报送底稿、评估体系与审计报告 | 月度闭环覆盖主要环节，评估指标达标且审计可查 |

**实施顺序的三个"不要"**：不要在 Phase 0 之前选框架；不要在数据契约未定时做多 Agent；不要在没有评估指标时扩大自动化范围。

**与工程实现的衔接**：本仓库 `ins_am_agent/` 已给出 A 到 D 四层的零依赖参考实现，可直接作为 Phase 1 与 Phase 2 的起点；Phase 3 的 ALM 与配置部分需要接入真实负债现金流与资本计量口径。

## 7. 常见问题

| 问题 | 回答 |
| --- | --- |
| 为什么不做一个大模型 Agent 搞定全部？ | 上下文装不下全部数据；出错无法定位；无法单独验收；改一处牵连全局。按"独立数据、独立方法、独立输出、独立责任人"四条判断是否拆分。 |
| 会不会取代研究员？ | 不会。Agent 承担取数、初筛、测算与初稿，研究员的时间转向判断、质疑与外部沟通；样本外的判断仍是人的工作。 |
| 内部数据不能出内网怎么办？ | 模型与工具层私有化部署，数据不出域；对外展示统一使用公开数据复刻版本。 |
| 报告口径由谁负责？ | 口径必须唯一且有责任人；报送与披露材料需双人复核，Agent 输出仅为底稿。 |
| 出错了怎么追责？ | 全链路留痕：输入指纹、模型版本、工具调用、结论、签批人。 |
| 为什么不让 Agent 直接下单？ | 受托责任与操作风险不可转移；下单与签批保留给人。 |
